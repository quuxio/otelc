# Node launch input evidence

<!-- markdownlint-disable MD013 -->

The source adapter retains candidate input evidence alongside each explicit-runtime launch. This records the requested launch, its fixed generated recipe, resolved preload entries, what the loader/compiler read and returned, and separately witnessed module-body entry. It is not an action witness, downstream receipt proof or protection from a hostile application that can write its own runtime directory. Independent consumer qualification and complete dependency closure remain open.

## Public recipe

Use the [public source launcher](node-source.md), selecting an original entry, project root, common policy and fresh private runtime directory. For example:

```sh
bin/quux-otelc --config /path/to/otelc.toml node \
  --language typescript --backend native \
  --root /path/to/project --entry /path/to/project/app.cts \
  --runtime /tmp/otelc-input-run -- 7
```

The Python producer selects a supported Node executable, pins argv to its resolved path, captures its content/version/module ABI/platform/architecture, generates its private plan/bootstrap and records the exact application argv, cwd and launcher PID. Bootstrap paths are absolute, including when the caller chooses a relative runtime directory. The original request keeps caller paths separately from their resolved origins, application arguments, common policy and selected compiler/lane. A policy loaded from TOML retains the exact stable read and text that produced the parsed policy; a programmatic `Policy.parse` request explicitly has no source file.

`otelc.node_recipe.verify(runtime, original_request, manifest, producer=approved_producer_root)` reconstructs the fixed argv, plan and bootstrap from original intent. It does not execute a command selected by evidence. A different entry, cwd, runtime, argument, compiler/lane, selection, generated file set or bootstrap fails even if its new content hash is internally consistent. Keep the original request independently when qualifying a provider; replacing both request and evidence with a different request is not proof of the original launch.

The source loader reads original application files and records the bytes before transformation. The launcher waits for application exit and the separate SDK report before rechecking retained inputs. It returns failure for changed or unavailable evidence, preserving an existing non-zero application result. Direct callers of `otelc.node.command` must perform this final verification themselves; constructing argv is not successful qualification.

## Versioned files

The launch and final input records use source evidence `schema_version = 5` and module execution protocol 1. The separate request and preload formats are version 1. Common policy remains schema 3 and SDK status remains schema 1. Consumers must explicitly support source5/execution1: versions1–3 lacked successive request/compiler/preload bindings, and version4 did not distinguish returned bytes from actual module-body entry or deferred/re-entered loads. Plain lanes use the `node-plain` prefix. All retained files are producer-created with mode0600 in the owned mode0700 runtime directory.

`otelc.node.protocols()` is a metadata-only public handshake. It returns exactly `schema_version`, `kind`, `source`, `execution`, `request`, `preload` and `sdk`; the current values are `1`, `"otelc.node.protocols"`, `5`, `1`, `1`, `1`, `1`. It does not prepare or launch an app, invoke Node, change the common plan response or declare a provider qualified. Consumers can cache it once per immutable provider, then independently verify each prepared manifest and recipe.

| File | Meaning |
| --- | --- |
| `node-request.json` | Original caller request, common policy and optional original TOML identity/text, requested/resolved paths, selected Node/compiler/lane, application arguments and private allowlisted environment records. |
| `node-launch.json` | Fresh launch ID, original request, language/backend/lane, entry/package context, Node identity, producer Python/adapter/npm source inventory, selected observer/HTTP product, resolved plan/digest, generated file identities, argv/cwd/launcher PID, separate tooling environments and resolved preload entries. |
| `node-sources.jsonl` | Synchronous read/emit journal. Each row keeps its physical origin; equal content at different paths/URLs does not merge identities. |
| `node-module-SHA256.txt` | Exact private compiler/hook output or source-map bytes, named by content digest. These are evidence files, not replacement application modules on disk. |
| `node-inputs.json` | Final `verified` or `failed` result. A verified instrumented result binds the launch manifest and final SDK report identities and records application/SDK PIDs. `action_delivery_verified` is always false. |

Input identities contain an absolute `path`, `resolved_path`, SHA-256 and byte `size`; producer symlink files also retain their link target. Read journals retain `requested_path` separately from the resolved physical origin. A configuration symlink retargeted to a different file with identical bytes still fails the final origin check. Producer directory symlinks and unreadable tooling trees are refused rather than omitted. Directory inventories include the complete installed files, including optional platform packages and any present development packages; they are not an assertion that every inventory file executed.

The fixed environment allowlist is declared in `otelc/node_recipe.py` and mirrored by the startup reader. Each key has either `state = absent`, or `state = present` with its exact private value and SHA-256. Empty values are present; missing keys and wrong hashes fail validation. This is not a general environment dump. Keep these files private, since launch settings and TOML text can contain sensitive local information. Runtime-identity probes remove `NODE_`, `OTEL_` and `OTELC_` variables while preserving OS settings. Preload resolution explicitly restores only `NODE_PATH` and `NODE_PRESERVE_SYMLINKS`, with derived condition/symlink flags. Neither probe executes application preloads or applies application Node compile-cache settings. The real application keeps its inherited settings.

A first `startup` journal row records the actual source-loader PID, Node executable, cwd, application argv, Node exec argv and allowlisted environment before the application entry loads. Missing, duplicate, out-of-order or mismatched startup evidence fails final verification; its PID must agree with the independent SDK checkpoint. A changed generated plan is refused before installing probes. Plain JavaScript uses no loader, so it retains requested launch evidence without claiming an in-process startup receipt. Ambient CommonJS preloads execute before this observation boundary; their actual effects and dependency closure need separate evidence.

## Preload entry bindings

The `preloads` object retains each original `--require`/`-r`, `--import` and custom-loader specifier with its option position and cwd. The parser follows Node's double-quote/space grammar, including literal tabs, single quotes and backslashes outside quotes. It does not interpret `NODE_OPTIONS` as a POSIX shell command or rewrite application flags. Node remains responsible for validating the complete option string at launch.

The producer invokes a fixed resolver helper with the selected Node binary. It uses public `createRequire().resolve` and `import.meta.resolve` APIs and never imports or requires the resolved application modules. The helper's identity, exact tooling argv, condition/symlink flags and explicit resolution environment are retained. Relative `NODE_PATH` values use the original cwd. File entries retain their URL, exact bytes, literal requested path identity or absence, resolved origin and nearest package context. Builtins and non-file URLs have separate kinds. A changed/missing file, same-byte alias retarget, changed package context, altered request order or different tooling recipe fails verification. The final verifier reads these records and files without executing recorded commands.

The resolver forwards ordered addon and synchronous-ESM require flags (including the experimental aliases), custom conditions, global-search-path flags and symlink flags. These settings can change the chosen export or whether a preload resolves at all. Boolean option tokens are retained intact rather than dropping an inline value. Matched require/import fixtures compare the recorded file with actual execution under disabled and re-enabled `node-addons` and `module-sync` conditions. This preserves resolution evidence; it does not make the instrumented profile compatible with flags that disable its own native observer or bootstrap module loading.

Entries retain declared CommonJS-before-import order and every repeated request; they do not fabricate execution counts. Node's normal cache can execute repeated identical requires/imports once. Functional fixtures audit actual application effects, covering mixed CJS/ESM preloads, paths containing spaces, package export conditions, relative `NODE_PATH`, duplicates and exactly-once execution. Missing preloads are rejected before any earlier application preload executes during launch preparation.

The record explicitly says `coverage = resolved_entries_and_nearest_package_context`. This does not inventory every transitive dependency, package search-path absence or custom loader action. Non-file preloads and custom loaders carry explicit gap tags. Do not promote that entry binding into complete build/loader closure or per-action attribution.

Journal kinds `source`, `compiler_config` and `package_context` bind the actual original bytes read. `absent_config` and `absent_package` retain absence where a later-created file could change configuration or module format. The TypeScript reader observes root and resolved `extends` configuration reads, including files outside the project root. Non-regular inputs are refused through non-blocking opens, so a substituted FIFO cannot hang before validation. An occupied final evidence filename is preserved and makes a successful application launch fail; an existing application failure remains the launcher result.

Each `module_requested` starts a distinct `load_id`, retaining its original source path/URL, logical name and JavaScript/TypeScript kind. Kinds `compiled`, `instrumented` and `loaded` distinguish compiler emission, probe insertion and uninstrumented hook return. They retain that load identity, original source hash/path, logical source name, original URL, format supplied by the compiler/loader (or `node-detected` when unspecified), output digest/size/file and optional source-map digest/file. Repeated imports with distinct URLs or repeated attempts do not collapse. Every attempted in-scope load needs a completed hook result. An application that catches a compiler/probe refusal can continue its own work, but the CLI reports failed input verification instead of treating missing instrumentation as success.

## Returned attempts and body entry

An emission is returned code, not proof that Node executed it. Ambiguous JavaScript can first pass through a deferred goal and then re-enter the loader with a known module format. Both original attempts and all their content-addressed bytes remain in the journal. The TypeScript Preserve fallback is explicitly `module`, matching the existing plain compiler execution profile; it is no longer written as `node-detected` in a compiled receipt. Known JavaScript formats also drive the parser's goal, including ESM files that contain no import/export statement.

Selected instrumented outputs and plain/otherwise unselected TypeScript outputs declare a closed `body_entry` observation delta: `schema_version = 1`, concrete `goal` (`module` or `commonjs`) and the approved absolute `source-inputs.ts` helper path. A collision-free prolog calls that helper before user module statements and static initialisers. Hashbangs/directives are retained, and maps are composed after insertion. Plain TS has this metadata-only observation helper, with no function/metric/trace probes or SDK; raw compiler output remains a separate artifact.

Only a real prolog call writes `execution_started`. Its closed fields are `kind`, `execution_protocol` (1), `pid`, `load_id`, original `path`/`url`/`logical_source`, `source_sha256`, `emission_kind`, `emission_sha256` and concrete `format`. The helper looks up the already published returned emission to bind its digest, avoiding a self-referential source hash. The final check binds the actual application PID, original input and exact returned bytes, and rejects changed format/digests, duplicate entry, unknown protocol fields or an entry preceding its emission.

If the same original URL re-enters before a prior witness is attempted, `module_reentered` binds the new load to `previous_load_id`. This records order and makes no causal claim about an engine retry. Final `module_outcomes` distinguishes `body_entered`, `unentered_before_same_url_entry` and `not_observed`. The unentered outcome requires a complete earlier emission and a retained same-origin chain ending in a later witnessed entry. Its `resolved_format` remains null: the earlier body did not have an observed execution format. A known failed/contradictory witness, missing compiler/probe phase or missing chain cannot be forgiven because a later load entered. Unobserved unselected JS stays explicitly unavailable.

This witness proves body entry at the injected helper, not module completion, selected function execution, unchanged bytes after an arbitrary following loader, export or downstream receipt. `module_execution_protocol = 1` and `module_execution_observation` describe this evidence in the final report. Plain native JS reports `native_plain_unavailable`, rather than claiming zero module executions. `action_delivery_verified` remains false. Independent consumers must still check the raw journal, retained artifacts, generated/actual module context, SDK accounting and decoded signals.

TypeScript attempts also require a `compilation` record. Its `compiler` object identifies the fixed compiler path/version/backend, cwd, native argv or API method, transformer profile and content-addressed `files`. The `input`, `options`, raw `output` and raw `map` artifacts are separate from the original source and remapped/probed output. Native evidence retains the actual augmented input, generated config, raw emitted bytes and preparation map before deleting its private workspace. The generated input/config must remain byte-identical across the actual compiler call. CJS `.ts` inputs use a private `.cts` name so an unrelated private/ancestor package type cannot change the requested format. API evidence retains the exact source string and numeric compiler-option object passed to `transpileModule`; the pinned transformer implementation belongs to the adapter closure. The native preparation map binds the original source path and decoded text; UTF-8 file bytes and decoded input text have separate hashes. Final checks validate the fixed compiler recipe, every artifact and the raw-output-to-compiled-output link.

The original file identity is separate from all emitted identities. A preceding loader that changes the original source bytes is refused. Known entry/package changes are refused before the application entry is loaded; final checks detect mutations during execution.

## Qualification boundary

Plain JavaScript runs Node directly, retaining entry/tool/runtime identities but no interposing source-load journal. Plain TypeScript records compiler/loader reads and metadata-only body entry without function/metric/trace probes or an SDK. Source observations currently cover the adapter's in-root JS/TS loading profile; outside-root imports, ambient preload dependency closure, arbitrary custom loaders, native application addons, worker/VM contexts and general build-system inputs remain incomplete. Package records describe the nearest package visible to our reader, not an independent observation of every Node resolver read. An unspecified returned format is retained separately from a witnessed body's concrete format. The fixed recipe, startup receipt and body-entry helper do not substitute for independent consumer validation.

Node interprets `NODE_OPTIONS` before explicit CLI options, and environment `--require` entries precede the producer's CLI bootstrap. The original option string is retained without changing or re-executing its application preloads during planning. See [Node's option-order rules](https://nodejs.org/api/cli.html#node_optionsoptions). Independent replay qualification and broader preload dependency closure remain required.

The initial manifest can be large because it inventories the installed dependency files. This preparation and final verification occur outside application operation timing. They still contribute to overall launch/shutdown cost and must not be described as free. A verified input record says nothing about whether selected application actions were observed, whether spans were lost or whether the downstream Collector/Tempo received them. Check those independently using SDK accounting, decoded telemetry and oteleq qualification.
