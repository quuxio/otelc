# Automatic context propagation and lifetime spans

Updated 8 October 2026. This is the implementation plan for C, C++, Rust, Python, Java, JavaScript, TypeScript and Go. Function spans are delivered for all eight; the work below extends their relationships and adds **automatic object / resource lifetime spans**. Plan entries are proposed until marked complete with a merged PR and test evidence.

## Product contract

Application and dependency source stays unchanged. Use common schema-2 configuration, private generated/compiler input, launch agents and runtime hooks. Existing annotations may guide selection, but adding annotations, imports, guard fields, decorators or probe calls is never an acceptance requirement. Preserve layouts, signatures, return values, exceptions, cancellation and application scheduling. A metrics-only lifetime guard does not deliver automatic lifetime spans.

Context propagation means capturing a trace identity when work is submitted, restoring it while that work runs, and restoring the worker's previous context afterwards. A child may start or finish after its parent ends. Keep that parent relationship without stretching the parent's duration or waiting for the child in application code. Preserve sampling decisions through excluded functions, rejected observations and asynchronous handoffs. Reused workers must never inherit a previous request.

Distributed propagation uses W3C `traceparent` and `tracestate` through explicitly qualified client/server integrations. Validate IDs, lengths, versions, flags, duplicate headers and bounded tracestate; discard invalid remote context without affecting the request. Respect valid explicitly supplied application context, avoid duplicate instrumentation, and exclude telemetry's own network traffic. Do not copy arbitrary application headers, baggage, credentials, URLs, arguments or exception messages into telemetry. Existing OpenTelemetry context interoperability needs its own coexistence tests; do not replace an application's global SDK/provider.

Automatic lifetime spans measure a declared boundary on selected types/resources:

- `object`: successful language-defined initialisation to completed destruction/drop. Failed construction is not a successful lifetime.
- `resource`: successful acquisition/initialisation to an existing close/dispose operation. An unsuccessful close leaves the resource open unless the qualified API specifies otherwise.
- `collection`: admitted allocation/initialisation to observed garbage collection. Collection time is nondeterministic and is not destruction or a leak verdict.

Resource adapters identify existing acquisition/release APIs externally. Do not infer an arbitrary method named `close` as a correct resource boundary. Each admitted instance has a process-unique token independent of its address. Do not export addresses or add per-instance metric labels. Object copying creates a new instance; logical moves/drop boundaries follow the language's declared semantics. Completed spans link to creation context instead of keeping a function tree buffered until destruction or collection. Span links permit lifetimes to cross threads, requests and service operations without making GC the parent function's measured duration.

The runtime stores bounded identity/timestamp/type/context metadata, never strong references to application objects, frames, tasks, futures or payloads. Lifecycle observers may use weak/phantom references or VM tags. They must not replace user finalisers, resurrect objects, force collection or force originally stack-allocated values to escape. An object still live at shutdown has no invented completion time: report an incomplete/censored observation and current live count. Process abort cannot guarantee export.

## Common configuration and reporting

The first implementation adds `[propagation] tasks = true` and `http = false`, both defaulting to false. Propagation requires `traces.enabled=true`. All language resolvers carry the same fields and report unsupported requests explicitly; parsing a valid future policy does not mean it can run. Language-specific integration names/version requirements belong under `adapters.<language>` when each integration is actually implemented.

Reuse `[lifetimes] enabled`, `boundary`, `include`, `exclude` and `runtime.max_live_lifetimes`. This existing section remains unavailable until a declared boundary is implemented. The lifetime delivery will use the common trace transport, sampling and bounded export queue, and export both span and metric evidence. Keep type selection/exclusion independent of function selection. Proposed resource acquisition/release bindings will be typed and validated before launch rather than unvalidated text substitutions.

Keep continuation reservations bounded by `runtime.max_active_calls`, separate from active function frames. Report pending contexts and capacity/hook/incomplete losses. A rejected continuation invalidates the affected local tree rather than exporting misleading fragments. Local subtree ownership must eventually be keyed separately from global trace ID: simultaneous requests in one global trace can have different remote parents and local roots.

Lifetime accounting needs its own bounded registry and loss reasons for capacity, unsupported boundaries, duplicate/stale completion, missed lifecycle events and shutdown. Export admitted/completed/current-live counts and completed-duration histograms by type/boundary; use span-only instance tokens when required for correlation. No raw addresses or object payloads. Sampling a lifetime must not corrupt aggregate live counts or change application object retention.

Ordinary function probes alone cannot prove all these boundaries. |

Support is per qualified integration and toolchain, not every scheduler, framework or runtime version merely because a language is listed. `doctor`/inspection must expose the qualified mechanisms and reject requested missing features.

## Delivery sequence: individual PRs

1. **Python asyncio context plus common policy** (implemented in [PR #32](https://github.com/quuxio/otelc/pull/32); [qualification and example](python-task-context.md)): unchanged internal fixtures, bounded reservations, concurrent/late children, cancellation/factories/context isolation. Preserve the previous default of independent scheduled roots when propagation is off.
2. **Shared distributed carrier fixtures and Python HTTP**: golden W3C vectors, local subtree IDs independent of global trace ID, inbound/outbound spans, independent service identity and no telemetry recursion. Two instrumented processes must produce one stored trace; also test a client with existing valid/invalid application headers.
3. **Python automatic resource/collection lifetime spans**: constructor and declared resource boundary observers, weak identity registry, standalone linked lifetime spans and metrics. Validate retention, constructor/close failures, duplicate completion and shutdown. Keep unsupported class shapes explicit.
4. **JavaScript context, HTTP and lifetime spans**, each as its own PR. Qualify callbacks, concurrent requests, worker transfers and weak collection independently.
5. **TypeScript context/HTTP qualification and lifetime spans**, separate PRs over the shared Node runtime and TS compiler/emission fixtures.
6. **Java context, HTTP and lifetime spans**, separate PRs; constructor-chain and virtual-thread fixtures must precede any claim of support.
7. **Go context, HTTP and lifetime spans**, separate PRs; preserve original escape/lifetime semantics and test GC/cleanup limitations.
8. **Rust typed backend, context, HTTP and lifetime spans**, separate PRs; pin and doctor the compiler backend, then prove moves/drop and executor boundaries.
9. **Native common context plus C propagation/resources/typed lifetimes**, separate PRs and explicit library bindings.
10. **C++ propagation and automatic lifetime spans**, separate PRs; ABI, object size/alignment, copy/move traits and exception cleanup must match the ordinary build.
11. **Mixed-language interoperability and overhead acceptance**: full service-chain matrix, shared schema conformance, stack/Grafana examples and paired benchmarks. Record which framework/toolchain combinations passed; do not extrapolate from internal fixtures to untested production libraries.

Before each PR, state the exact boundary, assumptions and acceptance tests. Run focused checks while implementing, then `make check`, independent minimum 80% component coverage and Sonar. Merge only a green reviewed final head to `main` as `quuxio`; update this plan and support docs with evidence. Compiler prerequisites may be delivered first, but never mark a language's lifetime spans complete merely because infrastructure exists.

## Equivalence qualification with oteleq

Use [oteleq](https://github.com/quuxio/oteleq) alongside the semantic and telemetry tests for each language milestone. Its [initial Rust workload comparator](https://github.com/quuxio/oteleq/blob/main/docs/workload-comparison.md) compares repeated captured byte channels and requires an expected decoded telemetry witness on each instrumented attempt. It accepts all eight language IDs, but only the diagnostic Python task capture is integrated now; semantic discovery, automatic generation and typed state observers remain outstanding.

The Python task milestone has been exercised twice without instrumentation and twice with the real launcher in fresh private workspaces. Exact stdout/stderr/exit matched, each instrumented run decoded the expected eight spans, and no losses or pending contexts were reported. Retained corpus, source/policy and artefact hashes, raw process output, runtime reports and OTLP bytes supply the evidence. A deliberately altered instrumented output was detected as `different_observed`. These are scoped diagnostic workload observations, not a production or hidden-state qualification.

For subsequent context and automatic object / resource lifetime spans, supply qualified observers for results, existing close/drop events, retention, receiver/global/argument mutations and relevant layout/introspection. Do not infer unchanged object state from stdout or compare exact GC times, random IDs or cross-host timestamps. Preserve all source/dependency files and place captures/generated helpers outside the target repository. Keep independent baseline, instrumented-on and supported off/fault controls; the initial comparator implements baseline/on only, so extend it with explicit capability checks before claiming more lanes.

Reports must say **equivalence over these tests and observations**, list the concrete corpus, artefact class, compared dimensions and gaps, and fail on unstable controls, incomplete requested capture, source changes or missing instrumentation evidence. Full typed graphs, alias/cycle handling and function inventory need their own oteleq PRs before they can qualify those dimensions. A scoped comparator success supplements the focused tests, minimum 80% component coverage and stored-span checks; it does not replace them.

## Focused acceptance tests

- Same source/dependency hashes, stdout, return/exception identity, object sizes and relevant introspection between ordinary and instrumented executions; existing annotation and externally selected variants.
- Parallel roots and reused worker threads; sibling tasks remain siblings. Parents finish before children start; cancelling before start releases the reservation. Eager factories, failed submission, recursive submission and explicit isolated contexts do not leak or cross-parent.
- Sampling zero/full/intermediate, capacity exhaustion and slot reuse; a dropped subtree cannot become a newly sampled root. Failed export, partial-success acknowledgement, delayed storage and shutdown with unfinished work remain visible losses.
- Two and three processes/languages share IDs and correct client/server parent links. Invalid/duplicate/oversized headers create safe new roots. Remotely unsampled context stays unsampled. Concurrent remote parents sharing one trace ID do not collide. Clock skew is not misreported as a parenting bug.
- Successful, failed and delegated constructors; implicit cleanup, copy/move, cross-thread close/drop, reused addresses and double completion. Existing close errors retain the declared boundary's semantics.
- Weak-reference/phantom/VM tests prove the observer does not keep an object alive. Test cycles, custom finalisers, resurrection, absent collection and collection after the creation request has ended. Never require an exact natural GC completion time.
- Objects still live at shutdown are incomplete; no completed lifetime span or duration is invented. Registry/queue/export limits expose losses and cannot block the application.
- Stored lifetime spans have type/boundary/status and creation links; stored request/task spans have correct causal parents. Do not require a child's timestamps to be contained in a completed parent, or compare clocks across hosts as if synchronised.
- Benchmarks compare ordinary, instrumented-disabled, metrics-only, function tracing, context propagation and lifetime tracing, plus combined modes. Record throughput, latency percentiles, allocation/GC pressure and loss. Agree workload-specific overhead thresholds before calling the system production-qualified.

## References and design constraints

The implementation uses [W3C Trace Context](https://www.w3.org/TR/trace-context/) and the [OpenTelemetry context contract](https://opentelemetry.io/docs/specs/otel/context/). Mechanisms above are implementation choices to qualify, informed by [Python task context](https://docs.python.org/3/library/asyncio-task.html#asyncio.create_task), [Python weak references](https://docs.python.org/3/library/weakref.html), [Node async context](https://nodejs.org/api/async_context.html), [ECMAScript finalisation semantics](https://tc39.es/ecma262/multipage/managing-memory.html#sec-finalization-registry-objects), [JVM TI](https://docs.oracle.com/en/java/javase/21/docs/specs/jvmti.html), [Go cleanup constraints](https://pkg.go.dev/runtime#AddCleanup), [Rust drop semantics](https://doc.rust-lang.org/reference/destructors.html) and [Clang front-end extensions](https://clang.llvm.org/docs/LanguageExtensions.html). These references establish available primitives, not proof that an otelc adapter is implemented.
